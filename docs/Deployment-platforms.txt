CHIEF AGENT — LOCAL/PRIVATE DEPLOYMENT

This replaces the former direct-worker, plaintext .env and two-service setup instructions. Read Service-Lifecycle.md, HTTP-Transport.md and Maintained-Runtimes.md. A verified software baseline is not certification of an installed Folio or operational database.

FOLIO
The intended target is Xubuntu 26.04 LTS, installed by the user. Xubuntu lists 26.04 and 24.04 as supported and 25.x as end-of-life: https://xubuntu.org/releases/
VM results apply to the recorded VM configuration. Folio hardware, graphical login, reboot, installed permissions, certificate lifecycle and real backup/restore require on-device acceptance. No real/Folio migration or restored-state promotion is authorized by this package.

SOFTWARE AND PRIVATE STATE
Verify the source archive and manifest before extraction. Keep immutable source, its matching interpreter/environment and writable private state separate. Never copy a virtual environment between platforms. Install from release/*-hashed.txt with hash verification and binary wheels. The platform inventories record actual versions; the Playwright catalogue is not the selected browser.
Run Chief as a normal dedicated OS user. Use private Unix permissions or restrictive verified Windows ACLs. Keep keys, browser profiles, private configuration, databases, backups and TLS material outside source and evidence archives. Provision model keys through private model setup, not service definitions or command arguments.

INSTANCE PREPARATION
The deployment prepare-preview command creates a NEW isolated preview directory and exercises a verified B.5 backup/restore prerequisite before every schema step. It prompts privately for the preview Owner password. It cannot prepare production or unlock quarantined restores.
Production preflight requires an explicitly reviewed, already prepared instance and matching schema fingerprint. It never migrates production. Do not remove quarantine markers, fabricate production markers or point an isolated configuration at operational data to bypass these safeguards.

A production service configuration is non-secret JSON. In addition to the existing absolute state/database/schema fields it must now contain:

  "public_host": "chief.example.com"
  "trusted_tls_proxy": "127.0.0.1"
  "farm_operations": "DISABLED"

Replace the example hostname only during real deployment. `public_host` is a DNS certificate hostname without a scheme, path or port. `trusted_tls_proxy` must be one explicit same-host loopback IP. Production startup fails if either HTTPS field is absent or invalid. The dashboard backend is fixed to 127.0.0.1. `farm_operations` defaults to DISABLED when omitted and accepts only DISABLED or ENABLED.

Setting `farm_operations` to ENABLED is an operational approval step, not a software-install step. This repository prepares and tests that gate but does not change any real production configuration to ENABLED.

INSTALL READINESS
Before installing service definitions, run `python -m deployment install-readiness` in a review shell with the absolute production config, absolute project/interpreter paths, target platform/account, and the independently recorded backup pins (`backup-directory`, manifest SHA-256, source-tree SHA-256 and schema SHA-256).

The install-readiness command does not install, start, stop or enable services. It does not perform DNS/TLS/network checks, promote restores, change Farm approval or migrate the database. It validates the prepared production instance, private-state filesystem readiness, the pinned browser identity with native sandbox required, the pinned operational backup, schema agreement between that backup and the production instance, and the complete three-service definition set. It returns metadata only and restores process environment selections before returning.

`SOURCE_READY_FOR_INSTALL_REVIEW` means those source/local gates passed. It is not deployment approval and does not prove DNS, certificate renewal, firewall policy, proxy installation, physical-device behavior or restore promotion.

SERVICES
Use deployment.launch with an absolute reviewed instance configuration for dashboard, worker and scheduler. Generate all THREE startup definitions through deployment.service_files; generation does not install or validate them. Stop manual copies first. Verify ownership, readiness, cooperative stop and restart for each component.
Linux definitions target the user's systemd manager and include `ConditionUser=<reviewed-owner>` so accidental installation under another user/root fails closed. Windows definitions use least-privilege interactive-token logon tasks: no stored password or unattended pre-login promise. macOS remains generated-only and unqualified. A forced stop leaves ambiguous work for review, not automatic replay.

BROWSER
Set browser_runtime in the service configuration to the non-secret JSON containing the absolute executable, version and SHA-256. Production browsing requires explicit qualification; changed executables fail closed. Keep native sandboxing enabled. Use Ubuntu's standard system-owned browser and OS integration; do not disable AppArmor or add --no-sandbox. OS package installation may require sudo; Chief runtime does not.

NETWORK AND HTTPS
Production application traffic is HTTPS-only. Chief itself remains on 127.0.0.1 and rejects plaintext requests in production even from loopback. The reviewed same-host TLS terminator must present a trusted certificate for public_host, preserve Host, overwrite X-Forwarded-Proto with https and forward only to the loopback Chief listener. Chief does not trust forwarded client identity or forwarded Host as authority.

In production the backend also requires the actual Host authority to match the reviewed `public_host`. Localhost/IP aliases, alternate hostnames, explicit ports and ambiguous authorities are rejected before application dispatch even through the trusted TLS proxy. Authentication cookies are Secure + HttpOnly + SameSite=Strict under production HTTPS; authenticated mutations still require same-origin Origin proof and the Chief CSRF token.

The runtime emits HSTS only on verified production HTTPS responses and adds nosniff, frame denial, no-referrer and a restrictive Permissions-Policy.

DNS, certificate issuance/renewal, firewall rules, proxy installation and verification are intentionally deferred to the actual deployment phase because they depend on the selected host/domain. Do not expose the loopback backend directly to a LAN/public interface as a shortcut.

APP EXPERIENCE
The web manifest supports an app-style browser window where browser installation is available. It is not a signed native installer, does not start services and does not cache private data offline. Real website login requires a private graphical session and separate provider/site acceptance.

ROLLBACK AND RESTORE
Stop all three components before selecting the verified rollback source and compatible interpreter; retain the private state target. Review interrupted scheduler cycles and ambiguous actions before restart. Software rollback does not restore data or unlock quarantine. Operational restoration requires the B.5 integrity and isolated-restore path followed by separate deployment acceptance. Source archives are not operational backups.

The install-readiness gate verifies an existing backup against explicit manifest/source/schema pins; it never creates a backup implicitly and never promotes an isolated restore. Credentials and browser/session secrets remain outside the ordinary operational snapshot and must be recovered or reprovisioned through their separate protected process.

ACCEPTANCE
Report exact source, runtime, tests/skips, OS user, service lifecycle, permissions, containment limits, HTTPS trust and backup/restore results. Distinguish Windows, Ubuntu VM and physical Folio evidence. See Users-and-access.md for human permissions.
