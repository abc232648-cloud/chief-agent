# Chief Update Center

The update target is Chief itself. Job, Farm and companion PWAs remain compatibility consumers, not independently installed products in this Update Center. Existing dependency discovery remains read-only.

## Available software

The publisher verifier accepts a bounded, signed Chief release envelope and verifies its repository, stable channel, sequence, commit, source manifest, archive identity, expiry and declared Windows/Linux targets. It uses Ed25519 with the context `chief-release-envelope-v1` followed by a zero byte. The signature covers the canonical JSON payload (sorted keys, compact separators, ASCII escapes, no NaN); the public key must come from separately provisioned installation policy. A key inside downloaded metadata is never trusted.

No production publisher key is included. Publisher signing and installation trust provisioning must be established separately before real releases can use this path. Synthetic test keys are generated in memory and are not release credentials. Verification errors return fixed messages rather than input contents or private paths.

The policy file has exactly `version` (1), `repository` (`abc232648-cloud/chief-agent`), `minimum_sequence` (nonnegative integer), and `keys`. Each key has exactly `key_id`, `public_key` (base64 raw 32-byte public key), timezone-aware `valid_from`/`valid_until`, and boolean `revoked`. Provision this file in private operator-controlled storage, separately from the release. Downloaded envelopes cannot add or rotate keys. The sequence floor is not a substitute for publisher key revocation.

An envelope has exactly `key_id`, `payload`, and base64 `signature`. Its payload includes `format_version` (1), `product` (`chief`), `repository`, `channel` (`stable`), positive `sequence`, immutable 40-character `commit`, `archive_sha256`, `archive_size`, existing Chief release `manifest`, `issued_at`, `expires_at`, and `targets`. Each target declares `os` (`windows` or `linux`), `architecture` (`x86_64` or `aarch64`), inclusive `python_minimum` and exclusive `python_before` as three-part versions. Declaring a target does not certify tests on that target. Duplicate fields, unsupported fields, duplicate targets, expired/revoked keys, future issue dates and validity periods over 31 days are rejected.

Artifact verification checks every ZIP member against the existing source-package manifest and the signed digest. Package bounds, path containment, case collisions and operational/private file exclusions are enforced before inert staging. Files are not extracted or executed. Existing staged slots are not overwritten.

## Operator verification and staging

`python -m application.update_verify --envelope ABSOLUTE_ENVELOPE --trust-policy ABSOLUTE_POLICY` checks publisher metadata only. Add `--archive ABSOLUTE_ARCHIVE` to verify package bytes too. Without an instance, replay protection is limited to the supplied policy floor; no durable acceptance is claimed.

Add `--config ABSOLUTE_PREPARED_INSTANCE_CONFIG` to bind the signed sequence in the existing private database. The command does not initialize or migrate a database. Concurrent retries are idempotent; a different envelope at the same sequence or an older sequence is rejected. Revocation and expiry are rechecked on retries. Interrupted database writes roll back both the receipt and the sequence head. Quarantined restores remain blocked. Database restore/administrator tampering is outside this local receipt's anti-replay guarantee: a restored installation must remain quarantined for reconciliation.

Add `--current-manifest ABSOLUTE_CURRENT_MANIFEST` for read-only planning against an operator-supplied current release and the current Chief capability catalog. This checks actual host OS, architecture and Python against signed targets, then retains dependency/regression/model/benchmark requirements. It does not infer successful tests from metadata. Operational schema migrations remain blocked even if a release declares them reversible. The current manifest is an operator input, not independent proof of the running source.

Inert staging additionally requires all of `--archive`, `--config`, `--current-manifest`, `--staging-root ABSOLUTE_EXISTING_PRIVATE_DIRECTORY`, and `--confirm-private-storage`. A blocked preflight prevents staging. A successful result is `STAGED_NOT_INSTALLED`; acceptance, backup and human activation authority are still absent. Failure after recording a valid publisher receipt can leave that receipt but never an installed release; retry the same exact signed envelope. Incomplete slots have no activation authority.

The Chief Updates page displays recorded verification separately from operator-reported update activity. Technical fingerprints are under expandable details. A recorded signature check does not imply current key validity, compatibility or installation.

## Recovery prerequisite

`update_center.recovery.guarded_recovery` connects the existing B.5 backup/isolated restore drill to managed-writer ownership. It refuses to run while any dashboard, worker, scheduler, scheduler-cycle or approved-action component owns its lock. It does not stop or kill services. Ownership remains held across the maintenance context; closing it invalidates the live-lock flag. A verified backup and quarantined restore remain available after an interrupted maintenance context, without automatic replay or deletion.

The recovery result reports its actual database-only or explicitly selected-file coverage. Credentials and browser sessions still need separate protected recovery. It does not infer a complete operational inventory, freeze external/manual writers, certify deployment recovery, or authorize activation. Source rollback identity is verified before and after the drill. Recovery destinations cannot be inside the software source. No application rows or schema are changed by this preparation.

Verification/staging alone does not grant installation permission. The manual lifecycle below adds candidate execution, human review and locked source selection. It does not download releases, install dependencies, migrate operational schemas, certify real deployment backup/restore or restart Chief. There are no separate PWA/domain update controls and no unattended self-modification.

## Managed source selection

`update_center.managed.ManagedInstallation` provisions a new private source-slot root from an explicitly pinned baseline. Existing roots are never adopted or overwritten. Each source slot is checked against its full manifest, including rejection of extra files and executable bytecode caches. Managed launches use `-B` to avoid creating caches. Signed source packages can be staged separately; changes to root requirements files are refused because the interpreter/dependency environment needs separate qualification. The interpreter executable is pinned at provisioning. This is not an attestation of every installed library.

Internal selection mechanics retain the previous slot and write an interruption journal before changing the selected source. The fixed read-only probe checks existing database schema and catalog composition; it neither initializes the database nor runs queued work. A normal probe failure restores the previous source pointer. An interrupted switch blocks managed service startup until exact-transaction recovery verifies the previous source and its probe. Recovery changes source selection only, never restores operational data or starts services. These checks cover process interruption; power-loss durability and filesystem behavior still require deployment qualification.

`deployment.service_files` can generate optional `--managed-installation` definitions pointing to a stable launcher source outside the switched slots. Existing unmanaged definitions remain unchanged. The managed entrypoint retains the normal instance/schema/identity/HTTPS checks. Each component rechecks the selected source after obtaining its ownership lock, preventing an old source selected before maintenance from starting after a switch. Generated definitions are review artifacts; no services are installed or enabled.

The source-switch and recovery methods are called through `ManualUpdater`, which binds the exact current source/schema, re-verifies publisher trust, computes the current dependency plan, checks human and component authority, and holds the B.5 recovery locks throughout selection. A separate `chief.update_source_selection` capability describes these mechanics; `chief.update_planning` remains non-executing and no AgentRegistry grant is added. Candidate execution is trusted local Python execution with a reduced environment, not an operating-system sandbox for hostile publisher code. Real service restart/HTTPS/device acceptance remains separate.

The acceptance runner copies only manifest-listed source into a new private execution directory and executes explicit required test files using the pinned interpreter, an isolated home/temp area and a reduced environment. Both the immutable candidate and tested source identities are checked afterwards; generated scratch files never become installed source. It requires a current reauthenticated installation administrator, explicit approval to execute reviewed publisher code and no policy prohibition. It records actual test counts and exact plan/source references in existing private `control_state` storage. Missing reports, missing required coverage, failures or skips cannot produce passing evidence. Unimplemented model/benchmark qualification and migrations block this runner. Raw output stays in private test storage; audit records carry references only. This is not full deployment acceptance or an installation approval. Browser/runtime configuration and external consumer acceptance must be available for their required tests to pass; unavailable requirements block qualification rather than being skipped.

Linux interpreter entrypoints may use the normal final-file virtual-environment symlink, with both the resolved target and executable hash pinned. Linked parent directories remain forbidden. Repointing that link requires requalification; source, database and configuration link restrictions are unchanged.

Candidate tests and probes now use a bounded process supervisor. POSIX uses a new process group. Windows creates the process suspended, assigns it to a private kill-on-close Job Object, then resumes it; this also covers the Windows virtual-environment launcher and ordinary descendants. Helpers are terminated on normal exit as well as timeout/failure. Output is monitored against an 8 MiB default limit; brief polling overshoot is possible, so this is not a filesystem quota. This is lifecycle cleanup, not hostile-code isolation. The Windows design follows [Microsoft's Job Object contract](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

`UpdateApprovals` records a separate explicit human review of server-owned acceptance. It requires current sensitive installation authority, enabled update preparation controls and no policy prohibition. Test evidence must match the complete plan/current/candidate identities and contain no failures or skips; evidence older than 24 hours or dated in the future is refused. The review expires after five minutes and its claim is atomic and single-use, bound to the same human/session. Revocation, policy/control changes and changed evidence are rechecked at claim time. Neither review nor claim selects a source or grants an agent capability. The execution coordinator must still independently verify publisher trust, installation authority, backup/restore locks and all required consumer acceptance before calling internal selection mechanics.

Existing Job/Farm controls, identities, policy checks, audit records and workflows remain authoritative. No schema addition is needed for verification receipts, which use the existing `control_state` table. Ordinary software rollback returns to the previous source; operational data restore remains a separate, quarantined procedure.

## Interactive local workflow

Prepare the private managed root from the exact accepted baseline with `ManagedInstallation.provision`, including its source manifest, pinned interpreter, existing instance configuration and schema fingerprint. This creates source slots only; it does not install services or adopt an existing directory. Existing deployment service-definition generation accepts `--managed-installation` and keeps its stable launcher outside these slots. Provisioning and final on-device permissions/startup acceptance remain operator tasks.

Provide a separate local update policy with exactly `{"version":1,"validation":"ASK","selection":"ASK","recovery":"ASK"}`. Each operation may instead be `BLOCK`; `ALLOW` and extra fields are rejected. This file is reloaded for each authority check. It controls only this manual updater and does not replace the existing Job PolicyGate. Publisher public-key policy remains a separate file.

`python -m application.update_manage` has `validate`, `apply` and `recover` operations. Each requires absolute `--installation`, `--current-manifest`, `--trust-policy`, `--update-policy`, `--private-work-root`, plus `--confirm-private-storage`. It prompts privately for an existing Owner/Administrator sign-in, creates no Owner, never initializes a database and revokes its temporary session on exit. Passwords/session tokens are not command arguments or exported results.

For browser/companion requirements, supply `--test-config` pointing to a local JSON object with exactly `browser_runtime` (the existing pinned Chromium runtime descriptor) and `client_root` (the parent of the three built PWA repositories). Only those explicit environment inputs are passed to candidate tests. The runtime descriptor and every built client asset are hashed; changed inputs invalidate evidence at review and claim. This local runner uses Chromium, while the publisher's wider browser/device matrix remains separate qualification. Missing required browser/client inputs fail or skip tests and therefore cannot qualify selection. Arbitrary environment variables or provider credentials are not accepted in this file.

- `validate --archive ABSOLUTE_ZIP --envelope ABSOLUTE_SIGNED_ENVELOPE` imports a signed source candidate and runs its requirements after explicit `VALIDATE` confirmation. Alternatively use `--candidate SHA256` for an already staged candidate. Preserve the returned run reference; a pass is not installation permission.
- Stop managed Chief services through the existing reviewed service lifecycle. `apply --candidate SHA256 --run-id REFERENCE` requires a new sign-in and explicit `APPLY` confirmation, recomputes the plan, records a single-use review, verifies backup plus quarantined restore, and selects source under all five ownership locks. A live component blocks it; the updater does not kill services. Success means `SOURCE_SELECTED_RESTART_REQUIRED`, not deployment certified. Restart and qualify the services separately.
- `recover --candidate SHA256` requires a new sign-in and explicit `RECOVER` confirmation. It accepts only the exact interrupted transaction and pinned previous source, repeats locked recovery preparation, and selects the previous source. It never restores operational data, promotes a quarantined restore or replays an action.

The Chief Updates page shows publisher observations, recorded candidate counts and operator history separately. Source fingerprints remain under details. The browser does not accept arbitrary file paths, publisher keys, test outcomes or installation commands. Real release signing/trust provisioning, complete protected operational inventory, device acceptance and deployment certification remain open.
