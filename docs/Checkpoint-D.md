## Separate concepts

Shared Evidence has truth type MEASURED/OBSERVED/DOCUMENTED/INFERRED and an independent UNVERIFIED/PARTIALLY_VERIFIED/VERIFIED/DISPUTED/STALE verification state. It carries domain ownership, opaque source/content references, caller-supplied time provenance, UTC receipt/source timestamps, optional confidence/reliability and extensible B.5 clock metadata. Verification needs a basis reference; it is an assertion by an authorized caller, not automatic proof. Contradictions and their resolutions append events; no source overwrites another. Quality assessment history includes an input fingerprint covering verification and contradiction revisions.

Job CandidateFact still owns PROPOSED/USER_CONFIRMED/REVOKED. Migration inserts no evidence or fact links. Explicit `JobEvidence.adapt(fact_id, truth=...)` creates UNVERIFIED metadata referencing the legacy row without guessing source time, copying private text, or treating confirmation as generic verification. Direct links bind a content/source fingerprint. There is no unlink or destructive history operation in D. Changed content invalidates its old support; resolve metadata explicitly or use a new Job fact. Revoked/proposed facts are never claim eligible, even with VERIFIED evidence.

`JobEvidence.confirmed()` starts with the existing USER_CONFIRMED query. Unlinked facts retain behavior. Known adverse linked evidence removes a fact from new claim inputs; absent metadata or UNVERIFIED alone does not revoke the user's existing confirmation. Generation's exact-text validator, form validation and final-submit preflight remain the factuality checks. Job composition injects the adapter into generation, discovery and submission; explicit dashboard retry uses it too. Generic worker classes retain optional provider seams and legacy defaults for compatibility. Trusted callers constructing those classes directly must inject the Job adapter for D semantics; they are not independent authorization entry points.

## Data Quality

Version 1.0.0 reports freshness, source versus receipt time, completeness, contradiction, verification, clock quality, calibration and source reliability. Missing values stay UNKNOWN/None. Calibration applies to measured evidence. Unknown clock vocabularies remain UNKNOWN. A source timestamp in the future at receipt stays adverse even if later wall time catches up. The initial explicit freshness default is 365 days; `assess(max_age=...)` allows domain-specific policy, without deriving that policy from missing evidence. Calibration/reliability are supplied assertions, not device measurements performed by this engine.

Confidence is capped by supplied reliability and at 0.25 for adverse evidence; unknown confidence remains unknown. Sufficiency is SUFFICIENT/INCOMPLETE/INSUFFICIENT. Authority restriction is UNCHANGED/BLOCKED (the contract also supports REVIEW_REQUIRED). `restrict(existing_policy_decision)` can only retain or reduce permission. Sufficient evidence never converts ASK/BLOCK to ALLOW. Live quality is recomputed at claim use, so old assessment rows cannot hide later contradictions. Historical applications are not rewritten. This does not add locking across a user's later website interaction; final preflight revalidates as before.

## Additive schema and operational gate

Seven new tables: chief_evidence_migrations, shared_evidence, evidence_verifications, evidence_contradictions, evidence_quality_assessments, job_fact_evidence_links, decision_ledger. Fourteen triggers prevent UPDATE/DELETE of D history through ordinary SQLite writes. Composite domain foreign keys prevent cross-domain evidence relations. No existing table or row is rewritten. This is append-only service history, not cryptographic tamper-proof storage against an administrator with direct file access.

`database.evidence_migrations.migrate_isolated` requires the explicit isolated-development marker, a verified B.5 backup pinned to source/schema/manifest identity, and an intact quarantined restore receipt with exact legacy rows. It then migrates the original disposable C fixture under BEGIN IMMEDIATE. All D DDL and its ledger entry commit together or roll back, including interruption. Retry validates the D schema/checksum and requires the saved C legacy state still to match; after legitimate legacy changes, make a new verified recovery point. C's strict migration ledger remains byte-identical and usable. No API, startup migration, production migration command or quarantine unlock was added.

## Decision Ledger and privacy

The Chief-wide service accepts a domain/capability context and validated references. Every lookup is domain scoped. No Job/Farm sharing is inferred; no Farm behavior or RBAC is added. Identifiers/codes are bounded and reject narrative text, URLs and paths. This is not a general secret scanner: callers must supply opaque references, never credentials hidden in identifier strings. Original private payloads remain in their existing domain storage.

Job records intent, actual legacy policy decisions, low-risk action outcomes, command outcomes, approval attempts and explicit retry outcomes. Correlations reference commands, approvals, audit rows, applications, snapshots, events and linked evidence when available. Missing confidence/approver information stays unknown; no identity is invented. Ambiguous legacy reference ownership is omitted. Policy events name jobs.legacy:1.0.0; the existing PolicyGate remains enforcement authority and C's new engine remains comparison-only. Approval records and snapshots remain authoritative.

Ledger append supports caller-stable idempotency keys and rejects changed payload under a reused key. Job observation uses a fresh correlation per actual invocation. Failed observations expose an error and, where possible, an existing audit error. They never retry external effects or replace the original outcome. There is no ledger executor, replay or permission-granting path. An intent without an outcome is unresolved, never permission to repeat an action. Full process-crash atomicity across external websites and SQLite is not claimed.

Tests use synthetic data and no live email/website action.
