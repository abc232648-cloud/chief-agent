# Local service lifecycle

Dashboard, worker and scheduler are separate processes. The worker no longer runs scheduled work: install/start the scheduler explicitly. Domain controls, capability restrictions, Job PolicyGate, evidence and approval checks remain unchanged. Scheduling does not own worker status or heartbeat.

Start each prepared instance with `python -m deployment.launch --component dashboard|worker|scheduler --config ABSOLUTE_CONFIG_PATH`. The config accepts only `mode`, `state_root`, `database`, optional `schema_sha256`, `dashboard_port` and `browser_runtime` (an absolute non-secret qualified-browser configuration; see Maintained-Runtimes.md). Production uses `PRODUCTION` and the existing schema fingerprint/production marker preflight. Synthetic development uses `ISOLATED_DEVELOPMENT` and the existing isolated marker. Paths must be absolute, plain and within the private root. No credentials, shell commands or arbitrary environment dictionary belong in this file. Explicit service startup disables implicit `.env` loading. Provider secret references remain separately provisioned; missing credentials fail closed.

Generate reviewable definitions with `python -m deployment.service_files --platform linux|windows|macos --project ABSOLUTE_SOURCE --user OWNER --instance-config ABSOLUTE_CONFIG --output NEW_DIRECTORY`, optionally `--python ABSOLUTE_INTERPRETER`. Generation never installs/enables services. Linux definitions target the user's systemd manager. Windows definitions use the current owner's interactive session, least privilege and a logon trigger; no stored password or unattended boot promise. macOS templates are generated-only pending native validation. No administrator/root execution or public listener is required.

`--stop` requests cooperative shutdown for the recorded run identity, never kills a PID. Signals also request stop. The worker finishes its current guarded operation before relinquishing ownership, and does not claim another command after a stop. The scheduler finishes its current cycle. Stale stop files cannot stop a replacement process. Private `service-control` records indicate process readiness and run identity, not action success or external system health. The OS owner is trusted; these files do not provide remote authorization or isolation from that owner.

Worker ownership retains the existing database-adjacent lock and EXECUTING→REVIEW recovery. Scheduler process ownership and cycle ownership use separate retained OS-lock files. Every cycle persists a versioned `scheduler_cycle_v1` record in the existing `control_state` table before effects, then marks completion afterwards. Any interrupted/failed cycle remains ambiguous; later cycles refuse automatic replay. This deliberately stops all scheduling until operational review, even if a failure occurred before an external action. No automatic unlock/retry command is provided. The record is metadata, not permission or a replacement for Job audit/history. SQL schema is unchanged and ordinary B.5 DB backups include it.

Linux service definitions allow 30 seconds for stop before the supervisor may force termination. Forced termination is not successful draining: workers recover ambiguous actions to REVIEW and scheduler cycles remain blocked. Windows Task Scheduler's forced stop is likewise a crash boundary; use the cooperative CLI first and verify STOPPED. Dashboard transport currently bounds draining to its existing transport timeout; long-running dashboard operations require separate acceptance and must not be assumed completed after a forced stop.

For software activation/rollback, stop all three processes, verify STOPPED and ownership release, select the verified source/interpreter directory in the startup definitions, then start and verify readiness. Do not change the private state target. The immediate HTTP transport baseline lacks the scheduler journal gate: leave its worker/scheduler stopped if any `scheduler_cycle_v1` record is incomplete or unrecognized, and reconcile externally before a reviewed rollback. Data restore is separate: B.5 restored databases remain quarantined and none of these services may promote them. No real/Folio migration or data restore is authorized by this procedure.

Private instance configuration, state, control files, backups, credentials, browser profiles and generated TLS material remain outside software/evidence archives. Dedicated OS identity, installed TLS, real provider/browser targets, boot/logout behavior, power-loss durability, Windows filesystem races, long-action supervisor draining and real deployment backup/restore remain operational acceptance gates. User-manager/session tasks prove lifecycle mechanics, not complete OS containment.

References: [systemd service lifecycle](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html), [Windows logon triggers](https://learn.microsoft.com/en-us/windows/win32/taskschd/logontrigger), [Windows task logon types](https://learn.microsoft.com/en-us/windows/win32/api/taskschd/ne-taskschd-task_logon_type).
